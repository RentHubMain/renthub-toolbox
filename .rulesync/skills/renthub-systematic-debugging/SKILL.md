# 系统化调试

随意打补丁浪费时间，还会制造新缺陷；表面修复往往掩盖根因。

**核心原则：** 在尝试修复之前，**必须**先找到根因。只治症状的修复视为失败。

**违反本流程的字面要求，就是违反调试的精神。**

## 铁律

```text
未完成根因调查之前，不得提出修复方案
```

若第 1 阶段未完成，不得提出修复。

## 何时使用

适用于**任何**技术问题：

- 测试失败
- 生产环境缺陷
- 行为与预期不符
- 性能问题
- 构建失败
- 集成问题

**尤其要在以下情况使用：**

- 时间压力大（紧急时更容易猜）
- 「先 quick fix 一下」看起来很省事
- 已经试过多种修复仍无效
- 上一次修复没解决问题
- 对问题仍缺乏完整理解

**不要因为以下理由跳过：**

- 问题看起来简单（简单问题也有根因）
- 赶时间（慌乱只会增加返工）
- 管理者要求立刻修好（系统化比乱试更快）

## 四个阶段

必须**按顺序**完成每一阶段，再进入下一阶段。

### 第 1 阶段：根因调查

**在尝试任何修复之前：**

1. **仔细阅读报错信息**
   - 不要略过错误或警告
   - 其中常常已有直接线索
   - 完整阅读堆栈
   - 记录行号、路径、错误码

2. **稳定复现**
   - 能否可靠触发？
   - 精确步骤是什么？
   - 是否每次都会出现？
   - 若无法复现 → 先收集更多数据，不要猜

3. **检查近期变更**
   - 什么改动可能导致现象？
   - `git diff`、近期 commit
   - 新依赖、配置、环境差异

4. **多组件系统中收集证据**

   **当系统包含多段链路（如 CI → 构建 → 签名，或 API → 服务 → 数据库）时：**

   **在提出修复前，先加诊断输出：**

   ```text
   对每一段组件边界：
     - 记录进入该组件的数据
     - 记录离开该组件的数据
     - 核对环境/配置是否贯通
     - 检查各层状态

   运行一次，用证据标出「断在哪一层」
   再据此分析是哪一组件失败
   再针对该组件深入调查
   ```

   **多层系统示例：**

   ```bash
   # 层 1：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 层 2：构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 层 3：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 层 4：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **由此可知：** 哪一层失败（例如：密钥进工作流 ✓，工作流到构建 ✗）。

5. **追踪数据流**

   **当错误深埋在调用栈中时：**

   同目录下见 `root-cause-tracing.md` 获取完整「向上追溯」手法。

   **简要版：**

   - 错误值最初从哪来？
   - 谁用错误值调了当前层？
   - 持续向上追到源头
   - 在**源头**修，不在症状处修

### 第 2 阶段：模式分析

**先找规律再动手：**

1. **找正常样本**
   - 在同仓库找相似且**工作正常**的代码
   - 与坏掉的相比，正常长什么样？

2. **对照参考实现**
   - 若在实现某种模式，把参考实现**逐行**读完
   - 不要扫读
   - 理解透彻再套用

3. **列出差异**
   - 正常与异常之间有什么不同？
   - 逐条列出，再小也别默认「不可能有关」

4. **理清依赖**
   - 还依赖哪些组件？
   - 需要哪些设置、配置、环境？
   - 隐含假设有哪些？

### 第 3 阶段：假设与验证

**科学方法：**

1. **只形成一个假设**
   - 写清楚：「我认为根因是 X，因为 Y」
   - 要具体，不要空泛

2. **最小化验证**
   - 用**最小**改动验证假设
   - 一次只动一个变量
   - 不要同时改多处

3. **验证后再继续**
   - 有效？→ 进入第 4 阶段
   - 无效？→ 形成**新**假设
   - **不要**在失败假设上再叠补丁

4. **确实不知道时**
   - 明确说「我不理解 X」
   - 不要装懂
   - 求助或继续查资料

### 第 4 阶段：实现修复

**修根因，不治症状：**

1. **先写失败用例**
   - 最小可复现
   - 优先自动化测试；若无框架可用一次性脚本
   - **修复前必须有**
   - 编写规范的失败测试可配合 **`renthub-test-driven-development`** 技能（同仓库 `.cursor/skills/renthub-test-driven-development/`）

2. **单次只做一个修复**
   - 针对已识别的根因
   - **一次**只改一处
   - 不要「顺便」重构或捆绑其他改动

3. **验证修复**
   - 目标测试是否通过？
   - 其他测试是否仍全绿？
   - 原问题是否真正消失？

4. **若修复无效**
   - **停**
   - 数一数已试过几种修复？
   - 若 **少于 3 次**：带着新信息回到第 1 阶段重新分析
   - **若已达 3 次及以上：停**，并质疑架构（见下第 5 点）
   - **不要**在未做架构讨论前尝试第 4 种及以上「再试一次」

5. **若已失败 3 次以上：质疑架构**

   **可能说明架构有问题的迹象：**

   - 每次修复都暴露新的共享状态/耦合/别处的毛病
   - 修复需要「大重构」才能落地
   - 每次修完别处又出现新症状

   **此时应停并质疑根本：**

   - 当前模式从根本上是否合理？
   - 是否在凭惯性硬撑？
   - 应重构架构，还是继续打补丁？

   **在尝试更多修复前，先与人类协作者讨论。**

   这不是「假设错了」——而可能是**架构本身不合适**。

## 红灯 — 立刻停手并按流程来

若你发现自己这样想或这样做：

- 「先 quick fix，以后再查」
- 「先改 X 试试能不能好」
- 「一次改多处再跑测试」
- 「先跳过测试，我手动验」
- 「多半是 X，我先修上」
- 「没完全懂，但这样也许能行」
- 「文档说 X，我稍微改一下用法」
- 「主要问题是这些：[列出一堆修复，却未做调查]」
- 在追溯数据流之前就提出方案
- **「再试一次修复」（已失败 2 次以上仍继续）**
- **每次修完问题跑到另一处**

**以上任一条都表示：停。回到第 1 阶段。**

**若已失败 3 次以上：** 质疑架构（见第 4 阶段第 5 点）。

## 协作者在纠正什么

**若对方这样说，说明方式不对：**

- 「是不是其实没发生？」— 你在未验证前就假设了
- 「能不能先看到…？」— 你本应先加取证手段
- 「别猜」— 你在未理解前就提修复
- 「往深处想」— 要质疑基础，而不只是症状
- 「又卡住了？」（带情绪）— 当前打法行不通

**听到这些：** 停。回到第 1 阶段。

## 常见自我合理化

| 借口 | 事实 |
|------|------|
| 「问题简单，不用流程」 | 简单问题也有根因；流程对简单 bug 也很快。 |
| 「紧急，没时间走流程」 | 系统化比乱试更快。 |
| 「先试这个，再调查」 | 第一次修复就定下基调；一开始就要做对。 |
| 「等确认好了再补测试」 | 未测的修复站不住；测试先行才能证明有效。 |
| 「一次改多处省时间」 | 无法隔离哪条改动起效，且易引入新 bug。 |
| 「参考太长，我按理解改一点」 | 一知半解必踩坑；必须完整读完。 |
| 「我看到问题了，直接修」 | 看到症状 ≠ 理解根因。 |
| 「再试一次修复」（已失败 2+） | 3 次以上失败多属架构问题；要质疑模式，而非再赌一把。 |

## 速查表

| 阶段 | 主要工作 | 完成标准 |
|------|----------|----------|
| **1. 根因** | 读错、复现、查变更、取证 | 弄清 **是什么、为什么** |
| **2. 模式** | 找正常样本、对比 | 列出差异 |
| **3. 假设** | 立论、最小验证 | 证实或换新假设 |
| **4. 实现** | 写失败用例、修复、验证 | 缺陷消除、测试通过 |

## 当流程走完后仍「没有根因」

若系统化调查后，问题确实来自环境、偶现时序或外部依赖：

1. 视为已走完本流程
2. 记录已调查内容
3. 采用合理手段（重试、超时、更清晰的错误提示等）
4. 增加监控/日志便于下次查

**但：** 声称「没有根因」的案例里，约 **95%** 仍是调查不彻底。

## 配套材料

以下文件与本技能同目录，属系统化调试的补充手法：

- **`root-cause-tracing.md`** — 沿调用栈向上追到最初触发点
- **`defense-in-depth.md`** — 找到根因后，在多层增加校验
- **`condition-based-waiting.md`** — 用条件轮询替代拍脑袋的固定 sleep

**相关技能：**

- **`renthub-test-driven-development`** — 第 4 阶段第 1 步：写规范的失败测试
- 宣称修复成功前，务必再次验证行为与测试（完成前验证）

## 实际效果（经验量级）

- 系统化：约 15–30 分钟定位并修好
- 乱试：常达 2–3 小时原地打转
- 一次修对率：约 95% vs 约 40%
- 引入新缺陷：接近零 vs 较常见
