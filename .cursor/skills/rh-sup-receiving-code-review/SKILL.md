# 接收代码评审（Code Review Reception）

## 概述

代码评审需要**技术判断**，不是情绪表演。

**核心原则：** 先核实再落实。有疑先问。技术正确性优于社交舒适。

## 响应模式

```
收到代码评审反馈时：

1. 阅读：完整读完反馈，不急于反应
2. 理解：用自己的话复述要求（或提问）
3. 核实：对照代码库现实检查
4. 评估：对**本仓库**是否技术上成立？
5. 回应：技术层面的确认或有理有据的反驳
6. 落实：一次一项，每项后测试
```

## 禁止的回应

**绝不：**

- 「您说得完全对！」（明确违反 CLAUDE.md 类约定时）
- 「好观点！」/「反馈很棒！」（表演式）
- 「我这就改」（尚未核实前）

**应改为：**

- 复述技术要求
- 提澄清问题
- 若错误则用技术理由反驳
- 少废话多动手（行动优于言辞）

## 含糊反馈的处理

```
若任一条不清楚：
  停止 — 先不要落实任何项
  对不清楚的条目请求澄清

原因：条目可能互相关联。一知半解 = 落实错误。
```

**示例：**

```
协作伙伴：「修 1-6」
你理解 1、2、3、6，4、5 不清。

❌ 错误：先实现 1、2、3、6，稍后再问 4、5
✅ 正确：「我理解 1、2、3、6。需要先澄清 4 和 5 再继续。」
```

## 按来源处理

### 来自协作伙伴

- **相对可信** — 理解后再落实
- **范围不清仍要问**
- **不要表演式认同**
- **技术确认或直接开改**

### 来自外部评审者

```
落实之前：

  1. 对**本仓库**是否技术上正确？
  2. 是否会破坏既有功能？
  3. 当前实现是否有充分理由？
  4. 是否覆盖所有平台/版本？
  5. 评审者是否了解完整上下文？

若建议明显不对：
  用技术理由反驳

若难以快速核实：
  明说：「没有 [X] 我无法核实。应 [调查/询问/继续] 哪一种？」

若与协作伙伴先前决策冲突：
  先与协作伙伴讨论
```

**协作伙伴规则（示例）：**「外部反馈 — 存疑，但要认真核对」

## 对「专业」功能的 YAGNI 检查

```
若评审建议「正规实现」：

  在代码库中 grep 实际用法

  若未使用：「该端点未被调用。是否删除（YAGNI）？」
  若在用：再谈正规实现
```

**协作伙伴规则：**「你和评审都对我负责。不需要的功能就不要加。」

## 落实顺序

```
多条反馈时：

  1. 先把不清楚的全部澄清
  2. 再按此顺序落实：
     - 阻塞项（崩溃、安全）
     - 简单修复（笔误、import）
     - 复杂修复（重构、逻辑）
  3. 每项单独测试
  4. 确认无回归
```

## 何时反驳

在以下情况反驳：

- 建议会破坏既有功能
- 评审缺少完整上下文
- 违反 YAGNI（未使用功能）
- 对本技术栈技术上不成立
- 存在兼容/历史原因
- 与协作伙伴架构决策冲突

**如何反驳：**

- 用技术推理，不要情绪化防御
- 问具体问题
- 引用通过的测试/代码
- 若涉架构则拉上协作伙伴

**若不便当面反驳：** 可用约定暗号（原文示例保留）：`Strange things are afoot at the Circle K`

## 确认正确反馈时

当反馈**确实**正确时：

```
✅ 「已修。[简短说明改了什么]」
✅ 「确实如此 — [具体问题]。已在 [位置] 修复。」
✅ [直接修好并在代码中体现]

❌ 「您说得完全对！」
❌ 「好观点！」
❌ 「感谢指出！」
❌ 「感谢[任何内容]」
❌ 任何致谢式套话
```

**为何不说谢谢：** 行动胜于言辞。修好代码即表明你听进去了。

**若差点写出「谢谢」：** 删掉。改成陈述修复事实。

## 优雅承认反驳错了

若你曾反驳但事后证明你错：

```
✅ 「您是对的 — 我查了 [X]，确实是 [Y]。正在落实。」
✅ 「核实后您正确。我最初理解错因为 [原因]。正在修复。」

❌ 长篇道歉
❌ 为当初反驳辩解
❌ 过度解释
```

陈述事实，继续推进。

## 常见错误

| 错误 | 修复 |
|------|------|
| 表演式认同 | 复述要求或直接动手 |
| 盲目落实 | 先对照代码库核实 |
| 批量不测 | 一项一项、每项测试 |
| 默认评审永远对 | 检查是否会破坏功能 |
| 不敢反驳 | 技术正确性优先于舒适 |
| 部分落实 | 先澄清所有条目 |
| 无法核实仍硬上 | 说明限制，请对方定方向 |

## 真实示例

**表演式认同（差）：**

```
评审：「删掉遗留代码」
❌ 「您说得完全对！我这就删…」
```

**技术核实（好）：**

```
评审：「删掉遗留代码」
✅ 「正在查… 构建目标是 10.15+，该 API 需 13+。是否要保留以兼容旧版？当前实现 bundle ID 有误 — 修 bundle 还是放弃 pre-13？」
```

**YAGNI（好）：**

```
评审：「上完整指标：库表、日期筛选、CSV 导出」
✅ 「grep 后无调用该端点。是否删除（YAGNI）？还是我漏了用法？」
```

**条目不清（好）：**

```
伙伴：「修 1-6」
你理解 1、2、3、6，4、5 不清。
✅ 「理解 1、2、3、6。需要先澄清 4 和 5 再动手。」
```

## GitHub 线程回复

回复行内评审评论时，应在评论线程回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），不要只发顶层 PR 评论。

## 结论

**外部反馈 = 待评估的建议，不是必须执行的命令。**

核实。质疑。再落实。

不要表演式认同。始终技术严谨。
