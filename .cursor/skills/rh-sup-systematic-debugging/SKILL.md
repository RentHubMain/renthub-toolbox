# 系统化调试（Systematic Debugging）

## 概述

随机打补丁浪费时间，还会制造新缺陷；快修往往掩盖根因。

**核心原则：** **永远**先找根因再谈修复。对症式修补 = 失败。

**违反流程字面，就是违反调试精神。**

## 铁律

```text
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

若未完成阶段 1，**不得**提出修复方案。

## 何时使用

**任何**技术问题：

- 测试失败  
- 线上缺陷  
- 异常行为  
- 性能问题  
- 构建失败  
- 集成问题  

**尤其要用：**

- 时间紧（紧急时更容易瞎猜）  
- 「就一个小补丁」看起来很明显  
- 已经试过多种修法  
- 上次修完仍不对  
- 尚未完全理解问题  

**不要因为：**

- 看起来简单（简单 bug 也有根因）  
- 赶时间（慌乱只会返工）  
- 经理催「立刻修好」（系统化往往比乱撞快）  

而跳过本技能。

## 四阶段

**必须**完成当前阶段，才能进入下一阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读报错**  
   - 不要跳过错误或警告  
   - 往往已写明解法  
   - 读完整栈、行号、路径、错误码  

2. **稳定复现**  
   - 能否可靠触发？  
   - 精确步骤？  
   - 是否每次必现？  
   - 若不能复现 → 多收数据，**不要**猜  

3. **查近期变更**  
   - 什么变更可能导致？  
   - `git diff`、近期提交  
   - 新依赖、配置、环境差异  

4. **多组件系统里收集证据**  

   **当系统有多层（如 CI → 构建 → 签名，API → 服务 → 库）：**  

   **在提修复前加诊断输出：**  

   ```
   对每一层边界：
     - 记录进入该层的数据
     - 记录离开该层的数据
     - 核对环境/配置是否传到下一层
     - 检查每层状态

   跑一遍，拿到「断在哪一层」的证据
   再分析，锁定失败组件
   再对该组件深挖
   ```

   **多层示例（shell）：**

```bash
# 层 1：工作流
echo "=== Secrets available in workflow: ==="
echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

# 层 2：构建脚本
echo "=== Env vars in build script: ==="
env | grep IDENTITY || echo "IDENTITY not in environment"

# 层 3：签名脚本
echo "=== Keychain state: ==="
security list-keychains
security find-identity -v

# 层 4：实际签名
codesign --sign "$IDENTITY" --verbose=4 "$APP"
```

   **可看出：** 哪一层断（例如 secrets→工作流 ✓，工作流→构建 ✗）。

5. **追踪数据流**  

   **当错误深埋在调用栈：**  

   本目录内详见 `root-cause-tracing.md` 的反向追踪法。  

   **速览：**  
   - 坏值从哪来？  
   - 谁用坏值调了这里？  
   - 一路向上追到**源头**  
   - 在源头修，不在症状处贴膏  

### 阶段 2：模式分析

**先找模式再动手：**

1. **找正常范例** — 同库中类似但**工作正常**的代码  
2. **对照参考实现** — 若是照模式实现，**通读**参考，不要扫一眼  
3. **列出差异** — 工作版与坏版每一处不同，再小也别想当然「无关紧要」  
4. **理清依赖** — 还依赖哪些组件、配置、环境？隐含假设？  

### 阶段 3：假设与验证

**科学方法：**

1. **单一假设** — 写清：「我认为根因是 X，因为 Y」  
2. **最小验证** — **最小**改动验证假设；一次只动一个变量  
3. **再继续前核实** — 有效？→ 阶段 4；无效？→ **新**假设；**不要**叠罗汉式加修复  
4. **不知道就说不知道** — 「我不懂 X」；别装懂；求助或再查  

### 阶段 4：实现

**修根因，不是症状：**

1. **先写失败用例** — 最简单复现；能自动化则自动化；无框架则临时脚本；**修之前必须有**；写失败测试可配合 **`rh-sup-test-driven-development`**  
2. **单次单修复** — 针对已认定根因；禁止「顺便」重构捆绑  
3. **验证修复** — 该测过了？别测挂？问题真消失？  
4. **若仍无效** — **停**；数已尝试几次：<3 次 → 带新信息回阶段 1；**≥3 次 → 停并质疑架构（下条）**；**无架构讨论不要试第 4 种瞎修**  

5. **若已 ≥3 次失败：质疑架构**  

   **可能说明架构有问题的信号：**  
   - 每修一处别处又冒共享状态/耦合问题  
   - 修复需要「大重构」才塞得下  
   - 补丁制造新症状  

   **停，问根本：**  
   - 这模式根本上成立吗？  
   - 是否在惯性硬扛？  
   - 该重构架构还是继续打补丁？  

   **先与协作伙伴讨论**，再尝试更多局部修复。这不是「假设错了」，而是**架构可能错了**。

## 红线 — 停下并按流程走

若你发现自己这样想：

- 「先快修，以后再查」  
- 「改个 X 试试看」  
- 「一次改几处再跑测」  
- 「跳过测试，我手测」  
- 「大概是 X，先修 X」  
- 「没完全懂但可能管用」  
- 「文档说 X 我换个写法」  
- 「主要问题是：[列一堆修**法**却没调查过程]」  
- 未追踪数据流就抛方案  
- **「再试一次修复」**（已试过 2+ 次）  
- **每修一次问题换地方冒头**  

**以上任一条 = 停。回阶段 1。**

**≥3 次修复仍失败：** 见阶段 4.5，质疑架构。

## 协作伙伴的「你走偏了」信号

- 「那不是没发生吗？」— 你在假设未核实  
- 「能不能让我们看到…？」— 你该先加取证  
- 「别猜」— 你在无理解下抛修复  
- 「往深了想」— 要质疑根假设，不只症状  
- 「我们是不是卡住了？」（带情绪）— 路数不对  

**见到这些：** 停。回阶段 1。

## 常见自我合理化

| 借口 | 现实 |
|------|------|
| 「问题简单不用流程」 | 简单也有根因；流程对简单 bug 也很快 |
| 「紧急没时间」 | 系统化比乱猜快 |
| 「先试这个再调查」 | 第一个补丁定调；一开始就要对 |
| 「确认管用再写测」 | 未测的补丁站不住 |
| 「几处一起改省时间」 | 无法隔离谁生效，易引入新 bug |
| 「参考太长我按理解套」 | 一知半解必踩坑；要读完 |
| 「我看明白问题了」 | 看见症状 ≠ 根因 |
| 「再试一次」（已失败 2+） | 3+ 失败要质疑架构，不是再赌 |

## 速查

| 阶段 | 主要动作 | 成功标准 |
|------|-----------|----------|
| **1. 根因** | 读错、复现、查变更、取证 | 弄清 **什么** 与 **为何** |
| **2. 模式** | 找正常例、对照、列差异 | 找出不同点 |
| **3. 假设** | 立论、最小验证 | 证实或换新假设 |
| **4. 实现** | 失败测、单修、验证 | 缺陷消失、测试绿 |

## 当真「没有根因」时

若系统化调查后确属环境、时序、外部因素：

1. 你已走完流程  
2. 记录调查过程  
3. 做合理处理（重试、超时、更明错误信息）  
4. 加监控/日志备将来查  

**但：** 声称「无根因」的案例里 **95%** 是调查不彻底。

## 实际效果（经验数据）

- 系统化：约 15～30 分钟定位修复  
- 乱试：常 2～3 小时空转  
- 首次修对率：约 95% vs 40%  
- 引入新缺陷：近零 vs 常见
